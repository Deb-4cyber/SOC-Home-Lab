# DR-002: LSASS Credential Dumping (T1003.001) - Layered Defense Analysis on Windows 11

- **Date:** 08/20/2026
- **Author:** Deborah George
- **Environment:** SOC Home Lab (Win11-Client 192.168.10.30, Splunk Enterprise 10.4.1)
- **Summary:** Simulated LSASS memory credential dumping on a domain-joined Windows 11 endpoint using two documented techniques. All attempts were blocked by three independent defensive layers: Windows Defender behavioral detection and kernel-level LSA Protected Process Light (PPL).

## MITRE ATT&CK Mapping

| Tactic | Technique | Sub-technique |
|---|---|---|
| Credential Access | T1003 - OS Credential Dumping | T1003.001 - LSASS Memory |

LSASS (Local Security Authority Subsystem Service) stores credential material in memory for active logon sessions. Dumping this process memory is a well-documented adversary technique used to extract password hashes and Kerberos tickets for use in lateral movement.

## Attack Simulation Setup

- **Source/Target:** Win11-Client (192.168.10.30)
- **Target Process:** lsass.exe
- **Assumed Breach:** This simulation begins from an assumed breach. Initial access to Win11-Client is assumed to have already occurred, for example via phishing or social engineering. How that access was obtained is outside the scope of this report.
- **Decision:** Windows Defender was deliberately left enabled for the first two attempts to test realistic detection behavior before disabling it.

## Overview

This simulation attempted to extract credential material stored in LSASS memory on a domain-joined Windows 11 endpoint. LSASS holds password hashes and Kerberos tickets for active logon sessions, making it a high-value target for attackers who want to move laterally to other machines using stolen credentials. Windows Defender was deliberately left enabled for the first two attempts to test realistic detection behavior before disabling it. All attempts were ultimately blocked by three independent defensive layers.

Two techniques documented on MITRE ATT&CK T1003.001 were attempted. The first used ProcDump, a legitimate Microsoft Sysinternals tool that captures a full memory snapshot of a running process to a file. The second used a living-off-the-land approach, calling the MiniDump function from the built-in Windows component comsvcs.dll via rundll32.exe, avoiding the need to drop any external tool to disk. Both were blocked by Defender. After disabling Defender, a third attempt revealed a deeper blocking mechanism at the kernel level.

## Attempt 1: ProcDump (Defender On)

ProcDump is a legitimate Microsoft Sysinternals diagnostic tool that captures a full memory snapshot of a running process to a file. It was chosen to simulate an attacker attempting to dump LSASS process memory to extract stored credential material.

```
procdump64.exe -ma lsass.exe C:\lsass.dmp /accepteula
```

The command returned an access denied error immediately. Windows Defender simultaneously displayed a security alert flagging the attempt as `HackTool:Win32/DumpLsass.E` (severity: High) and logged the full command line path, confirming Defender was monitoring process arguments in real time rather than just scanning the file at rest.

## Bypass Test: Renamed Executable

To determine whether Defender's detection was filename-based or behavioral, `procdump64.exe` was renamed to `update.exe` to disguise the tool as a legitimate process.

```
update.exe -ma lsass.exe C:\lsass.dmp /accepteula
```

The same access denied error and Defender popup appeared with the identical detection signature `HackTool:Win32/DumpLsass.E`. This confirmed that Defender's detection is fully behavioral and argument-based, monitoring for any process targeting `lsass.exe` with memory-dumping flags regardless of what the tool is named. A simple filename change is not sufficient to bypass this control.

## Attempt 2: Living Off the Land via comsvcs.dll (Defender On)

Living off the land (LOTL) means abusing legitimate built-in Windows tools and components to carry out an attack, rather than dropping external tools to disk. Since ProcDump was blocked, this technique was chosen to test whether using a native Windows component would evade Defender's detection.

`comsvcs.dll` is a legitimate built-in Windows system file containing a `MiniDump` function originally designed for Windows crash reporting. It was called via `rundll32.exe`, a standard Windows utility for executing functions stored inside DLL files:

```
rundll32.exe C:\Windows\System32\comsvcs.dll, MiniDump <PID> C:\lsass.dmp full
```

The attempt was blocked again. Defender flagged it as `HackTool:Win32/DumpLsass.H`, a completely separate signature from the ProcDump detection, confirming Defender maintains dedicated individual detections per technique rather than a single generic LSASS dumping rule. Even a built-in signed Windows component was not sufficient to evade detection.

## Splunk Detection Evidence

Both blocked attempts were captured in Splunk via the Windows Defender Operational log (EventCode 1116):

```
host=Win11-Client sourcetype="WinEventLog:Microsoft-Windows-Windows Defender/Operational" EventCode=1116
| table _time, EventCode, Message
| sort -_time
```

| Time | Detection Name | Command Line Logged |
|---|---|---|
| 21:11:42 | HackTool:Win32/DumpLsass.E | update.exe -ma lsass.exe C:\lsass.dmp /accepteula |
| 21:17:46 | HackTool:Win32/DumpLsass.H | rundll32.exe comsvcs.dll, MiniDump 840 C:\lsass.dmp full |

**Sysmon EID 1 and EID 10 returned no results.** Defender intercepted both attempts before the processes could fully execute or access LSASS memory, meaning Sysmon had nothing to log. This confirms the Defender Operational log is the primary detection source for blocked LSASS dump attempts, not Sysmon.

## Attempt 3: Disabling Defender and PPL Discovery

After two blocked attempts with Defender enabled, Tamper Protection was disabled via the Windows Security GUI, then real-time protection was disabled via elevated PowerShell:

```powershell
Set-MpPreference -DisableRealtimeMonitoring $true
Get-MpComputerStatus | Select-Object RealTimeProtectionEnabled
```

`RealTimeProtectionEnabled` returned `False`, confirming Defender was fully off. Both techniques were retried. The comsvcs.dll command ran silently but produced no dump file. ProcDump returned:

```
Error opening lsass.exe (840): Access is denied. (0x00000005, 5)
```

Error code `0x00000005` is the Windows kernel returning Access Denied, indicating something below Defender was blocking access. The following registry query was run to investigate:

```
reg query HKLM\SYSTEM\CurrentControlSet\Control\Lsa /v RunAsPPL
```

Result:
```
RunAsPPL    REG_DWORD    0x2
```

`RunAsPPL = 0x2` confirms LSASS is running as a Protected Process Light (PPL) at the kernel level. This means the Windows kernel itself enforces access restrictions on LSASS memory independently of any user-space security software. Even a local administrator cannot read LSASS memory when PPL is active, because the kernel rejects the request before any tool can access the process. Disabling Defender makes no difference since PPL operates at a completely separate, lower level.

## Summary of Defensive Layers

| Layer | Mechanism | Result |
|---|---|---|
| 1 | Defender behavioral detection (command-line argument monitoring) | Blocked ProcDump and comsvcs.dll with separate dedicated signatures |
| 2 | Windows Defender real-time protection | Disabled via Tamper Protection toggle and PowerShell |
| 3 | LSA Protected Process Light (RunAsPPL = 0x2, kernel-level) | Blocked all attempts even with Defender fully disabled |

## Recommendations

1. **Maintain PPL as a baseline hardening control:** Ensure RunAsPPL is enabled across all domain-joined endpoints via GPO. This provides a kernel-level safety net that remains effective even if Defender is bypassed or disabled.

2. **Forward Defender Operational log to Splunk:** Sysmon alone missed both blocked attempts entirely. The Defender Operational log (EventCode 1116) was the only source that captured this activity. Ensure this log channel is included in forwarder inputs.conf on all endpoints.

3. **Alert on EventCode 1116 for DumpLsass signatures:**
```
sourcetype="WinEventLog:Microsoft-Windows-Windows Defender/Operational" EventCode=1116
| search Message="*DumpLsass*"
| table _time, Message
```

4. **Alert on Tamper Protection changes:** Defender EventCode 5007 logs configuration changes including Tamper Protection being disabled. In a mature environment this should trigger an immediate alert as it is a strong indicator of an attacker preparing to bypass endpoint protection.

## Lessons Learned

Going into this simulation the expectation was straightforward: run a documented technique, get a credential dump, move on. What actually happened was more instructive than a clean success would have been.

Both techniques documented on MITRE ATT&CK T1003.001 were blocked before producing any output. This was the first real exposure to how layered Windows security actually works in practice. Prior to this, the assumption was that Windows Defender handled endpoint protection as a single control. This simulation revealed that Defender and PPL are completely independent layers operating at different levels of the operating system, and defeating one has no effect on the other.

The rename bypass test was a particularly useful exercise. The intuition that changing a filename might evade detection turned out to be wrong, and understanding why (behavioral argument-based detection rather than filename matching) is a more valuable takeaway than simply knowing the technique exists.

From a red team perspective, this exercise demonstrated that bypassing modern endpoint protection requires significantly more patience, research, and creativity than running documented tools against a default configuration. A fully patched Windows 11 machine with default settings blocked every standard approach without any additional hardening beyond what ships out of the box.

For a blue team analyst, the more important takeaway is that the Defender Operational log captured everything while Sysmon captured nothing. Knowing which log source to look in, and why, is what separates a useful detection from a missed one.
