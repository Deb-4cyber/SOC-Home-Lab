# DR-001: Nmap Port Scan Against Domain Controller (DC01) - WFP Auditing Detection Gap

- **Date:** 08/11/2026
- **Author:** Deborah George
- **Environment:** SOC Home Lab (Splunk Enterprise 10.4.1, Windows Server 2022 DC, Kali attack box)
- **Summary:** Nmap reconnaissance scan against DC01 initially produced no Splunk detections, traced to WFP connection auditing being disabled by default. Auditing was enabled and the scan was re-detected successfully.

## MITRE ATT&CK Mapping

| Tactic | Technique | Sub-technique |
|---|---|---|
| Discovery | T1046 - Network Service Discovery | N/A |

The `-sV` and `-sC` flags enumerate service versions and run default NSE scripts against open ports, mirroring adversary behavior used to map out a network before further exploitation.

## Attack Simulation

- **Source:** Kali (192.168.10.40)
- **Target:** DC01 (192.168.10.20)

```
nmap -sV -sC 192.168.10.20
```

The scan enumerated all open ports, service versions, and revealed the DC hostname and domain name.

## Initial Detection Attempt (Failed)

```
host=DC01 sourcetype="WinEventLog:Security" EventCode=5156 Source_Address="192.168.10.40"
```

Returned no results even with time filter set to All Time.

## Root Cause Analysis

Investigated in order, ruling out simple causes first:

**1. Time window and clock drift:** Re-ran with All Time filter and verified clocks on both Kali and DC01. No drift found, timestamp mismatch ruled out.

**2. Sysmon network visibility:**
```
host=DC01 sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=3
```
Returned only one unrelated historical outbound connection. SwiftOnSecurity's Sysmon config logs outbound connections only by design, confirming Sysmon was never going to catch inbound scan traffic.

**3. WFP auditing:**
```
host=DC01 sourcetype="WinEventLog:Security" EventCode=5156
```
Returned zero events across all time, confirming WFP Connection auditing was disabled by default and had never logged any inbound connections. This was the root cause.

## Remediation

Enabled WFP Connection auditing on DC01 via elevated PowerShell:

```powershell
auditpol /set /subcategory:"Filtering Platform Connection" /success:enable /failure:enable
```

Verified with:

```powershell
auditpol /get /subcategory:"Filtering Platform Connection"
```

## Successful Detection

Re-ran the Nmap scan and searched Splunk:

```
host=DC01 sourcetype="WinEventLog:Security" EventCode=5156 Source_Address="192.168.10.40"
```

Returned 66 events in 15 minutes showing every port the scan hit and access frequency, confirming the detection gap was closed.

## Recommendations

1. **GPO baseline:** Deploy WFP Connection auditing (success and failure) across all domain-joined endpoints via Group Policy, eliminating reliance on per-host manual configuration.

2. **Automated port scan alert:** Build a Splunk correlation rule triggering when a single source IP hits more than 20 distinct ports within 5 minutes:
```
sourcetype="WinEventLog:Security" EventCode=5156
| bucket _time span=5m
| stats dc(Destination_Port) as unique_ports by Source_Address, _time
| where unique_ports > 20
```

3. **Reduce attack surface:** Restrict SMB (port 445) and other high-value ports to necessary source IPs via host firewall rules, limiting what a scan can enumerate.

## Lessons Learned

- No detection result does not mean no attack occurred, it may mean the right auditing is not enabled.
- Sysmon and Windows Security logs serve different purposes and neither alone provides complete network visibility.
- Ruling out simple causes first (time window, clock drift) before assuming a deeper problem saves significant investigation time.
