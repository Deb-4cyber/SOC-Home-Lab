## DR-001: Nmap Port Scan Against Domain Controller (DC01) - WFP Auditing Detection Gap

- **Date:** 08/11/2026
- **Author:** Deborah George
- **Environment:** SOC Home Lab (Splunk Enterprise 10.4.1, Windows Server 2022 DC, Kali attack box)

## Overview

An Nmap scan was run against the domain controller (DC01) from the Kali attack box, using the `-sV` and `-sC` flags to enumerate service versions and gather additional information (such as domain and hostname) from open ports. A Splunk query was run afterward to confirm the scan had been logged - this initial check came back empty, revealing a detection gap.

Investigation traced the gap to Windows Filtering Platform (WFP) connection auditing being disabled by default on DC01, meaning inbound network connections were never logged. After enabling WFP auditing via `auditpol` and re-running the scan, the second Splunk query successfully returned the full set of scan events.

## MITRE ATT&CK Mapping

- **Tactic:** Discovery
- **Technique:** T1046 - Network Service Discovery
- **Justification:** The Nmap scan performed in this simulation maps directly to MITRE ATT&CK's Discovery tactic, specifically T1046 (Network Service Discovery). The `-sV` flag enumerates the version of each service running on open ports, and `-sC` runs default NSE scripts, which in this case revealed the DC's hostname and domain name. This kind of enumeration is typically an adversary's first step after gaining network access, used to map out available services before further exploitation.

## Attack Simulation

**Command:**
```
nmap -sV -sC 192.168.10.20
```

**Source:** Kali (192.168.10.40)
**Target:** DC01 (192.168.10.20)

This command enumerates all open ports on the target domain controller. From the results, an attacker learns the exact service and version running on each open port, along with the domain and hostname of the DC - information that supports planning further attack steps.

## Initial Detection Attempt (Failed)

After running the scan, the following Splunk query was used to check whether it had been logged:

```
host=DC01 sourcetype="WinEventLog:Security" EventCode=5156 Source_Address="192.168.10.40"
```

This query returned **no results**, even after widening the time filter to All Time.

## Investigation / Root Cause Analysis

With the initial search coming back empty, the investigation ruled out possibilities in order rather than assuming the worst case first:

1. **Time window / clock drift** - Re-ran the search with an All Time filter to rule out a time-range issue, and checked the clocks on both Kali and DC01 to confirm they weren't drifted relative to each other. No drift was found on this run, so the gap wasn't a timestamp mismatch.

2. **Sysmon network visibility** - Checked Sysmon's own network connection telemetry:
   ```
   host=DC01 sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=3
   ```
   This returned only a single unrelated historical event (an outbound connection), confirming that the SwiftOnSecurity Sysmon config in use only logs **outbound** connections by design - it was never going to catch inbound scan traffic like this Nmap scan, so Sysmon wasn't the right data source for this detection to begin with.

3. **Windows Security log (WFP auditing)** - Checked whether Windows itself was auditing inbound connections at the OS level, via the Windows Filtering Platform:
   ```
   host=DC01 sourcetype="WinEventLog:Security" EventCode=5156
   ```
   This also came back empty - with **zero** WFP Connection events in DC01's history at all, not just for the scan window. This confirmed the root cause: WFP Connection auditing was **disabled by default** and had never been logging inbound connection attempts, which explains why the original scan produced no detections.

## Remediation / Fix Applied

WFP Connection auditing was enabled on DC01 via an elevated PowerShell session:

```powershell
auditpol /set /subcategory:"Filtering Platform Connection" /success:enable /failure:enable
```

Verified with:

```powershell
auditpol /get /subcategory:"Filtering Platform Connection"
```

This ensures both successful and failed inbound connection attempts are now logged to the Windows Security log, closing the visibility gap identified above.

## Successful Detection

With auditing enabled, the Nmap scan was re-run:

```
nmap -sV -sC 192.168.10.20
```

The same Splunk query was run again:

```
host=DC01 sourcetype="WinEventLog:Security" EventCode=5156 Source_Address="192.168.10.40"
```

This time the query returned results - roughly 66 events in the last 15 minutes, showing every port the scan hit and how many times each was accessed, confirming the detection gap was successfully closed.

## Recommendations

1. **Baseline via GPO:** Create a Group Policy Object to enable WFP Connection auditing (success and failure) on all domain-joined endpoints by default, rather than relying on manual configuration per host.
2. **Automated alerting:** Build a Splunk detection rule that alerts when a single source IP generates inbound connection events (EventCode 5156) against multiple distinct ports within a short time window - a classic port scan signature:
   ```
   sourcetype="WinEventLog:Security" EventCode=5156
   | bucket _time span=5m
   | stats dc(Destination_Port) as unique_ports by Source_Address, _time
   | where unique_ports > 20
   ```
3. **Reduce attack surface:** Restrict SMB (port 445) and other high-value ports to only necessary source IPs via host firewall rules, limiting what a scan like this can enumerate in the first place.
